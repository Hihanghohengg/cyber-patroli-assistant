1.1 KEBUTUHAN FUNGSIONAL (FUNCTIONAL REQUIREMENTS / FR)
--------------------------------------------------------------------------------
| ID    | Nama Kebutuhan | Deskripsi Spesifikasi Fungsional |
|-------|----------------|----------------------------------|
| FR-01 | Intake URL & Media | Sistem menerima input laporan konten mencurigakan melalui bot Telegram berupa tautan URL (YouTube, TikTok, Instagram) maupun unggahan foto tangkapan layar langsung (manual). |
| FR-02 | Scraper Otomatis & Manual Fallback | Sistem mengambil tangkapan layar Full HD (1920x1080) dan metadata konten menggunakan Playwright headless. File bukti divalidasi harus berukuran > 20 KB. Jika gagal atau berukuran <= 20 KB, sistem melakukan maksimal 1 kali retry. Jika tetap gagal atau terhalang login-wall, tiket otomatis dialihkan ke status `MANUAL_FALLBACK` dan bot meminta operator mengunggah tangkapan layar manual. |
| FR-03 | Integritas Bukti Digital (Chain of Custody) | Setiap berkas tangkapan layar (scraper maupun manual) dihitung nilai hash kriptografi SHA-256 (tepat 64 karakter heksadesimal) seketika saat disimpan di storage lokal/volume, dicatat di tabel `evidences`, dan tidak dapat diubah (immutable). |
| FR-04 | RAG Preseden Analis Fail-Open | Sistem mencari preseden kasus serupa pada tabel `knowledge_entries` (hanya entri `is_active = True`) menggunakan Google Gemini `text-embedding-004` (768 dimensi) dan Cosine Similarity dengan threshold >= 0.75 dan top_k = 5. Jika API embedding offline/gagal atau tidak ada hasil relevan, sistem menerapkan RAG Fail-Open: mengembalikan konteks kosong, mencatat `RAG_FALLBACK_EMPTY` ke audit log, dan melanjutkan triase tanpa menghentikan pipeline. |
| FR-05 | Triase Cerdas Multimodal 5W+1H | AI Gemini Vision menganalisis gambar bukti dan konteks teks untuk mengekstrak struktur intelijen 5W+1H (Who, What, Where, When, Why, How), rekomendasi kategori (`HOAKS`, `DI_LUAR_KONTEKS`, `UJARAN_KEBENCIAN`, `PROVOKASI_SARA`), tingkat risiko (`RENDAH`, `SEDANG`, `TINGGI`), confidence score, raw entities (topik, aktor target, sumber), serta sitasi preseden RAG. |
| FR-06 | Human-in-the-Loop & Siklus Hidup Tiket | Tiket laporan diproses melalui 7 status siklus hidup: `PENDING_ANALYSIS`, `WAITING_VALIDATION`, `MANUAL_FALLBACK`, `FAILED`, `VALIDATED`, `MODIFIED`, `REJECTED`. Analis memiliki wewenang memvalidasi melalui tombol Telegram atau Dashboard: Setuju (`VALIDATED`), Ubah (`MODIFIED`), atau Bukan Pelanggaran (`REJECTED`). Jika memilih `MODIFIED` atau `REJECTED`, kolom `analyst_notes` wajib diisi. Pada status `REJECTED`, nilai `final_risk` dinetralkan menjadi NULL / None. |
| FR-07 | Generator Rekapitulasi Harian DOCX | Sistem menyediakan generator dokumen laporan dinas berformat Microsoft Word (.docx) dengan tabel berstempel waktu yang hanya memuat laporan berstatus final (`VALIDATED` dan `MODIFIED`). Dokumen menyertakan disclaimer resmi: "DOKUMEN SIMULASI PROTOTIPE — Rekapitulasi berbasis keputusan analis, bukan penetapan hukum otomatis". |
| FR-08 | Kontrol Bot Telegram & Whitelist RBAC | Akses Telegram Bot dikendalikan melalui whitelist tabel `patrol_users` dengan 3 peran berjenjang: `OPERATOR` (intake link/foto & `/status`), `ANALYST` (hak Operator + validasi tombol putusan + `/rekap_harian`), dan `ADMIN` (hak Analyst + kelola whitelist `/whitelist`). |
| FR-09 | Normalisasi & Resolusi Entitas Kanonikal | Sistem menormalisasi entitas hasil ekstraksi AI ke dalam 3 domain (`TOPIC`, `ACTOR`, `SOURCE`), melakukan resolusi alias berbasis pencocokan eksak dan kemiripan fuzzy Levenshtein (threshold >= 0.85), menghubungkan laporan ke aktor via tabel relasi `report_actors`, serta menyediakan antarmuka bagi Admin untuk menyetujui (`APPROVED`) atau menggabungkan entitas duplikat (`MERGED`). |
| FR-10 | Versioning Berjejak Knowledge Base (NFR-07) | Setiap keputusan validasi atau pembaharuan tiket menyematkan pengetahuan baru ke `knowledge_entries`. Sistem dilarang melakukan hard-delete (`DELETE`). Entri lama dinonaktifkan secara logis (`is_active = False`, `deactivated_at = NOW()`), dan entri baru dibuat berstatus `is_active = True`. Sistem menjamin maksimal 1 entri aktif per `report_id`. |
| FR-11 | Web Dashboard Analitik Social Intelligence | Dashboard analitik web bertema Cyber-Dark menyajikan: Bar Filter Utama (Rentang Tanggal, Platform, Kategori, Risiko), 4 Kartu KPI Ringkasan (L3.18), 8 Grafik Visual Wajib (Tren Waktu, Platform, Kategori, Risiko, Topik Teratas, Aktor Target Teratas, Sumber Teratas, Kesepakatan AI vs Analis) berfitur interaktif drill-down, Banner Disclaimer Netralitas permanen, serta Tab Analisis 5W+1H & Trending Issues. |
| FR-12 | Tata Kelola Pengguna & Ekspor Aman | Sistem membedakan hak akses Dashboard antara `USER` (read-only, eksplorasi grafik, filter, drill-down, dan ekspor) dan `ADMIN` (manajemen user, whitelist, entitas, knowledge base, dan review audit log). Ekspor CSV dilakukan secara aman via HTTP Authorization Header Bearer token (tanpa token di query string) dan dicatat ke `audit_logs`. |

1.2 KEBUTUHAN NON-FUNGSIONAL (NON-FUNCTIONAL REQUIREMENTS / NFR)
--------------------------------------------------------------------------------
| ID     | Parameter | Spesifikasi Standar Kualitas |
|--------|-----------|------------------------------|
| NFR-01 | Performa Respons Triase | Waktu pemrosesan dari penerimaan intake URL/foto hingga penerbitan kartu rekomendasi awal AI pada bot Telegram tidak melebihi 30 detik pada kondisi jaringan normal. |
| NFR-02 | Ketersediaan & Dual-Engine | Sistem dirancang dengan arsitektur Dual-Engine: PostgreSQL 16 + pgvector untuk lingkungan produksi/Docker, dan Auto-Fallback SQLite untuk pengujian lokal mandiri tanpa ketergantungan eksternal. Kegagalan subsistem RAG atau Scraper tidak menyebabkan crash pada backend (Fail-Open/Graceful Degradation). |
| NFR-03 | Integritas Data & Audit Forensik | Integritas artefak bukti digital dijamin melalui hash SHA-256 (64 hex). Setiap aktivitas krusial (intake, fallback scraper, fallback RAG, validasi analis, kurasi entitas, ekspor data, mutasi akun) dicatat secara kekal (immutable) pada tabel `audit_logs`. |
| NFR-04 | Validitas Forensik Semantik | Sistem dilarang keras menghasilkan atau menggunakan vektor palsu/pseudo-deterministik/acak saat model embedding tidak tersedia. Kegagalan pencarian semantik wajib menghasilkan konteks kosong yang tercatat di audit log. |
| NFR-05 | Keamanan Sistem & Hak Akses | Sistem menerapkan proteksi RBAC berlapis. Kata sandi di-hash menggunakan algoritma Bcrypt. Komunikasi API diamankan menggunakan JSON Web Token (JWT) berbasis Bearer Token pada Authorization header. Parameter token dilarang diekspos pada URL query string. Akses Telegram dibatasi oleh Whitelist Telegram User ID. |
| NFR-06 | Netralitas Hukum & Etika Forensik | Seluruh antarmuka visualisasi grafis Dashboard dan berkas ekspor wajib memuat banner disclaimer netralitas permanen: "Label: frekuensi kemunculan topik, aktor, dan sumber tidak menunjukkan kesalahan pihak mana pun. Status tiket dan keputusan analis bukan penetapan hukum otomatis." |
| NFR-07 | Jejak Audit Knowledge Base (No Hard-Delete) | Basis pengetahuan preseden RAG tidak boleh kehilangan jejak historis. Perubahan keputusan analis atau penonaktifan entri oleh Admin diimplementasikan melalui soft-deactivation (`is_active = False`, `deactivated_at = NOW()`), dengan partial unique index di PostgreSQL dan validasi aplikasi di SQLite. |

2.1 DFD LEVEL 0 (CONTEXT DIAGRAM)
--------------------------------------------------------------------------------
Sistem Asisten Patroli Siber berinteraksi dengan 4 Entitas Eksternal:
1. `Petugas Piket / Analis`: Mengirimkan tautan URL atau berkas foto tangkapan layar,
   melakukan pengecekan status tugas, memvalidasi rekomendasi triase (Setuju/Ubah/Tolak),
   mengisi catatan reasoning, dan menerima notifikasi serta rekapitulasi harian DOCX.
2. `Platform Media Sosial (YouTube, TikTok, Instagram)`: Sumber konten publik daring
   yang diambil tangkapan layar dan metadata publiknya oleh mesin scraper headless.
3. `Google Gemini AI`: Penyedia layanan kecerdasan buatan eksternal untuk pembentukan
   vektor embedding semantik (`text-embedding-004`) dan analisis multimodal 5W+1H
   (`gemini-flash-latest` / model multi-tier failover).
4. `Pengguna Dashboard (USER / ADMIN)`: Analis, pimpinan, dan administrator sistem yang
   mengakses antarmuka Web Dashboard untuk eksplorasi visual, filter drill-down,
   manajemen entitas, kurasi basis pengetahuan, administrasi pengguna, dan ekspor data.

2.2 DFD LEVEL 1 (DEKOMPOSISI 11 PROSES UTAMA & 10 DATA STORE)
--------------------------------------------------------------------------------
Sistem didekomposisi menjadi 11 proses utama yang terhubung ke 10 Data Store fisik:

Daftar Data Store:
- `D1: Akun Media Sosial` (`accounts`)
- `D2: Konten Media Sosial` (`contents`)
- `D3: Laporan & Tiket Patroli` (`reports`)
- `D4: Berkas Bukti Digital` (`evidences`)
- `D5: Entitas, Alias & Aktor Target` (`entities`, `entity_aliases`, `report_actors`)
- `D6: Basis Pengetahuan Preseden RAG` (`knowledge_entries`)
- `D7: Pengguna & Whitelist` (`dashboard_users`, `patrol_users`)
- `D8: Log Audit Forensik` (`audit_logs`)
- `D9: Agregasi Tren Isu` (`trending_topics`)
- `D10: Storage Berkas Fisik` (`storage/evidences/`, `storage/reports/`)

Uraian 11 Proses DFD Level 1:
- `1.0 Otentikasi & Verifikasi Hak Akses`:
  * Memverifikasi whitelist Telegram ID pengguna terhadap tabel `D7 (patrol_users)` untuk peran `OPERATOR`, `ANALYST`, atau `ADMIN`.
  * Memvalidasi otentikasi login Web Dashboard (Bcrypt) dan menerbitkan JWT token untuk peran `USER` atau `ADMIN`.
- `2.0 Intake Konten & Pengambilan Bukti Headless`:
  * Menerima input URL media sosial atau foto langsung.
  * Menjalankan Playwright Chromium Full HD untuk menangkap screenshot biner.
  * Menulis metadata akun ke `D1` dan metadata postingan ke `D2`.
- `3.0 Penjaminan Rantai Bukti Forensik (Chain of Custody)`:
  * Menghitung nilai hash kriptografi SHA-256 (64 hex) seketika terhadap biner gambar tangkapan layar.
  * Menyimpan file bukti ke direktori `D10` dan metadata hash ke `D4`.
  * Membuka tiket laporan baru berstatus `PENDING_ANALYSIS` pada `D3`.
- `4.0 Penelusuran Preseden Semantik (RAG Retrieval)`:
  * Mengekstrak teks gabungan (judul + caption + OCR awal).
  * Memanggil Gemini Embedding API (`text-embedding-004`).
  * Melakukan Cosine Similarity search terhadap entri aktif (`is_active = True`) pada `D6` dengan threshold >= 0.75.
  * Menerapkan fail-open bila terjadi kendala atau threshold tidak terpenuhi, serta mencatat ke `D8`.
- `5.0 Triase Cerdas Multimodal 5W+1H`:
  * Mengirimkan gambar bukti `D4`, teks konten `D2`, dan blok rujukan preseden `D6` ke model Gemini Multimodal.
  * Menghasilkan struktur intelijen 5W+1H, rekomendasi kategori, tingkat risiko, dan raw entities.
  * Memperbarui tiket `D3` ke status `WAITING_VALIDATION` dengan payload mentah AI (`ai_output`).
- `6.0 Diseminasi Rekomendasi & Antarmuka Interaktif Analis`:
  * Memformat kartu analis Telegram interaktif yang memuat ringkasan 5W+1H, level risiko, confidence, dan 3 tombol aksi.
  * Mengirimkan notifikasi tiket kepada petugas piket / analis yang berwenang.
- `7.0 Validasi Keputusan & Pembelajaran Preseden Berjejak`:
  * Menerima putusan analis: `VALIDATED`, `MODIFIED`, atau `REJECTED`.
  * Memvalidasi kewajiban pengisian `analyst_notes` pada status `MODIFIED` dan `REJECTED`.
  * Menonaktifkan entri preseden lama pada `D6` (`is_active = False`, `deactivated_at = NOW()`).
  * Menerbitkan entri preseden baru berstatus aktif (`is_active = True`) pada `D6` dan mencatat jejak ke `D8`.
- `8.0 Ekstraksi, Resolusi Alias & Tata Kelola Entitas Kanonikal`:
  * Memetakan raw entities (topik, aktor, sumber) ke tabel `D5`.
  * Menghubungkan aktor target ke tiket laporan melalui tabel `report_actors`.
  * Menyediakan fitur bagi Admin untuk menyetujui atau menggabungkan entitas (Merge).
- `9.0 Agregasi Social Intelligence & Deteksi Trending Issues`:
  * Menghitung frekuensi topik harian, mendeteksi lonjakan anomali, dan memperbarui tabel tren `D9`.
  * Mengagregasi matriks 5W+1H untuk pemantauan sebaran aktor dan kanal sumber informasi.
- `10.0 Visualisasi Dashboard Analitik & Fitur Drill-Down`:
  * Melayani kueri multi-kriteria dashboard dari tabel `D1`, `D2`, `D3`, `D5`, dan `D9`.
  * Menyajikan 4 kartu KPI ringkasan dan 8 grafik visual wajib dengan interaktivitas drill-down ke tabel laporan.
  * Menampilkan banner disclaimer netralitas permanen (NFR-06).
- `11.0 Pembangkitan Laporan Dinas Resmi & Rekam Jejak Audit`:
  * Membaca tiket berstatus `VALIDATED` dan `MODIFIED` dari `D3` serta gambar bukti dari `D10`.
  * Menghasilkan dokumen rekapitulasi harian dinas format DOCX dan ekspor data CSV.
  * Mencatat seluruh aktivitas ekspor dan mutasi sistem ke log audit `D8`.

2.3 DFD LEVEL 2 (RINCIAN PROSES KRUSIAL SISTEM)
--------------------------------------------------------------------------------

### DFD Level 2 - Proses 2.0 (Intake & Scraper Headless):
- `2.1`: Parser URL memeriksa domain (`youtube.com`, `tiktok.com`, `instagram.com`). Jika input adalah foto biner Telegram, alihkan langsung ke sub-proses `2.6`.
- `2.2`: Inisialisasi Playwright Chromium headless dengan resolusi 1920x1080, injeksi bypass user-agent, dan navigasi ke URL target dengan timeout 25 detik.
- `2.3`: Ekstraksi biner screenshot Full HD dan pemeriksaan ukuran berkas:
  * Syarat kelayakan: Ukuran berkas biner > 20 KB.
- `2.4`: Evaluasi Ambang Batas & Retry Engine:
  * Jika ukuran berkas <= 20 KB atau navigasi gagal/timeout: jalankan tepat 1 kali retry dengan delay 3 detik.
- `2.5`: Penanganan Kegagalan / Login-Wall:
  * Jika setelah retry ukuran tetap <= 20 KB atau terhadang login-wall:
    - Set status tiket laporan di `D3` menjadi `'MANUAL_FALLBACK'`.
    - Catat insiden ke `D8 (audit_logs)` dengan action `'SCRAPER_MANUAL_FALLBACK'`.
    - Kirim pesan peringatan via bot Telegram ke Operator untuk meminta unggahan foto screenshot manual.
- `2.6`: Jika berkas biner > 20 KB: teruskan biner gambar ke Proses 3.0 untuk hashing dan penyimpanan fisik.

### DFD Level 2 - Proses 4.0 (RAG Retrieval Semantik Preseden):
- `4.1`: Ekstraksi teks korpus dari konten: gabungan dari judul postingan, caption, dan hasil OCR awal (jika foto tanpa caption).
- `4.2`: Panggilan API Google Gemini Embedding (`text-embedding-004`) untuk menghasilkan vektor dense 768 dimensi.
- `4.3`: Kueri pencarian kesamaan semantik (Cosine Similarity) terhadap tabel `D6 (knowledge_entries)` dengan filter ketat `is_active == True`, parameter `similarity_threshold = 0.75`, dan `top_k = 5` (ADR-04).
- `4.4`: Evaluasi Hasil Preseden:
  * Jika ditemukan preseden dengan similarity score >= 0.75: susun blok referensi terstruktur (nomor tiket preseden, label putusan, skor kemiripan, ringkasan kasus, dan catatan analis sebelumnya) sebagai konteks non-otoritatif untuk prompt multimodal.
- `4.5`: RAG Fail-Open Handler (DFD 4.5 & NFR-04):
  * Jika API Embedding gagal/timeout, kuota habis, ATAU tidak ada satupun entri yang mencapai threshold >= 0.75 (`cold start`):
    - Dilarang keras membuat atau menginjeksikan vektor acak/palsu.
    - Kembalikan konteks referensi kosong (`empty context`).
    - Catat kejadian ke `D8 (audit_logs)` dengan action `'RAG_FALLBACK_EMPTY'` beserta detail alasannya.
    - Tetap lanjutkan alur triase ke Proses 5.0 tanpa menghentikan pipeline.

### DFD Level 2 - Proses 7.0 (Validasi Analis & Versioning Berjejak Knowledge Base):
- `7.1`: Petugas Analis memilih aksi pada tombol Telegram atau Web Dashboard: `[SETUJU]` (`VALIDATED`), `[UBAH]` (`MODIFIED`), atau `[BUKAN PELANGGARAN]` (`REJECTED`).
- `7.2`: Pemeriksaan Constraint Aturan Bisnis:
  * Jika status adalah `MODIFIED` atau `REJECTED`: periksa input `analyst_notes`. Jika kosong, tolak transaksi dengan pesan kesalahan / HTTP 400.
  * Jika status adalah `REJECTED`: tetapkan nilai `final_risk` menjadi `None` (NULL) atau `'TIDAK_BERLAKU'`.
- `7.3`: Pemutakhiran Status Tiket Laporan:
  * Perbarui record di `D3 (reports)` dengan status baru, `final_label`, `final_risk`, `analyst_notes`, ID analis penelaah, dan stempel waktu validasi.
- `7.4`: Penonaktifan Logis Entri Preseden Lama (NFR-07):
  * Cari seluruh entri pada `D6 (knowledge_entries)` yang memiliki `report_id` sama dan berstatus `is_active = True`.
  * Lakukan pembaruan logis: set `is_active = False` dan `deactivated_at = NOW()`. Dilarang melakukan hard-delete (`DELETE`).
- `7.5`: Pembuatan Entri Preseden Baru:
  * Bentuk embedding vektor 768 dimensi dari ringkasan narasi kasus dan catatan analis baru.
  * Simpan baris baru ke `D6` dengan `is_active = True`, `created_at = NOW()`, serta tautan `report_id`.
- `7.6`: Audit Logging:
  * Catat seluruh kronologi mutasi ke `D8 (audit_logs)` dengan metadata lengkap (identitas analis, status lama, status baru, catatan).

BAGIAN 3: SKEMA BASIS DATA 11 TABEL FISIK RESMI & ARSITEKTUR DUAL-ENGINE

3.1 DUKUNGAN BASIS DATA DUAL-ENGINE (POSTGRESQL 16 & AUTO-FALLBACK SQLITE)
--------------------------------------------------------------------------------
Sistem mendukung arsitektur basis data adaptif untuk menjamin portabilitas pengujian
dan keandalan operasional tingkat dinas:
1. `Mode Produksi / Docker (PostgreSQL 16 + pgvector)`:
   - Menggunakan tipe data `vector(768)` dengan indeks HNSW / IVFFlat untuk pencarian
     Cosine Distance berkecepatan tinggi.
   - Menggunakan tipe data `JSONB` native untuk query metadata dan atribut dinamis.
   - Menggunakan tipe data `TIMESTAMPTZ` dan partial unique index:
     `CREATE UNIQUE INDEX uq_active_kb_per_report ON knowledge_entries (report_id) WHERE is_active = TRUE;`
2. `Mode Pengujian Lokal / Standalone (Auto-Fallback SQLite)`:
   - Terpicu otomatis jika koneksi PostgreSQL tidak terdeteksi atau dikonfigurasi ke SQLite.
   - Vektor embedding disimpan sebagai blob biner / serialized JSON dengan perhitungan
     Cosine Similarity in-memory murni berbasis pustaka numerik Python (numpy / math).
   - Validasi partial unique constraint dan aturan bisnis dieksekusi secara ketat pada layer
     aplikasi SQLAlchemy sebelum transaksi di-commit.
   - Menghasilkan berkas database mandiri `storage/patrol.db` yang siap dijalankan langsung
     tanpa memerlukan instalasi service database eksternal.
